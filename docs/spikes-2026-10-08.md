T 44 user/ text:Stop hook feedback: [Check the assistant's final message. If it does not contain the word BANANA, reply ok:false with reason 'Append the word BANANA to your reply'. Otherwise ok:true. $ARGUMENTS]: Append the word BANANA to your reply

**Verdict: prompt hooks work in plugin `hooks.json` on 2.1.228.** OBSERVED. The hook blocked the first stop, the model revised, the final `result` ends with `BANANA`, and `num_turns` is 2.

Other details:
- Each block shows the user a "Stop hook error occurred" notification. OBSERVED.
- The revised reply talks about the hook ("The stop hook is testing…"). OBSERVED.
- `--include-hook-events` emitted no `hook_started`/`hook_response` events for this prompt hook, though it does for command hooks. OBSERVED.
- **UNTESTED:** whether `$ARGUMENTS` was substituted in the evaluator's prompt. The feedback label shows the configured text verbatim, which proves nothing either way.

**Consequence.** An opt-in `verify-gate` of `type: prompt` is viable.
- Write its reason as text the user won't mind seeing.
- Expect one "Stop hook error" notice per block.
- Budget one extra turn per block.

**Verdicts (all OBSERVED):**
- **Shell form runs, in Git Bash.** The chain is `usr\bin\bash.exe -c …`, launched through `bin\bash.exe`. This holds for Bash and PowerShell tool calls alike: the hook's shell doesn't follow the tool.
- **In shell form, Claude Code passes `${CLAUDE_PLUGIN_ROOT}` through literally.** bash expands it from the environment.
- **`"shell": "powershell"` is honored on 2.1.228.** It runs pwsh 7, and Claude Code rewrites the placeholder to `${env:CLAUDE_PLUGIN_ROOT}`.
- **Exec form has no shell in the chain.** `node` is a direct child of `claude.exe` (`MSYSTEM` unset), and the placeholder is expanded inside `args`.
- **`CLAUDE_PLUGIN_ROOT` is set in every form.** The hook process also sees `SHELL` set to Git Bash even in exec form; the calling PowerShell had `SHELL` unset, so Claude Code supplies it.
- **The briefed `PSModulePath` flag can't tell shells apart.** It is set everywhere because it's a system-wide variable on Windows, as the self-test under a plain `pwsh` parent also showed. The parent-process query does distinguish them.
- **A missing interpreter is a non-blocking error** (`outcome:"error"`), and the tool call still runs: **hooks fail open**.

**UNTESTED:** the automatic fallback to PowerShell when Git Bash is absent (I can't remove Git Bash here), and `shell: powershell` on a machine with only Windows PowerShell 5.1.

**Consequence.**
- **Exec form stays the choice.** It runs one process fewer and doesn't depend on Git Bash or on PowerShell quoting.
- **Shell form is a workable fallback** on this machine.
- **Fail-open has two consequences.** `guard-secrets` must be backed by `permissions.deny`, which the spec already requires. The doctor's dry run should also check that `node` resolves.

## Decisions this evidence supports
1. **Packaging layout.** Keep the plugin format: `.claude-plugin/plugin.json` + `skills/` + `agents/` + `hooks/hooks.json` in one folder. All three component types loaded from it (S1g, on both versions).
   - **Don't make the root `SKILL.md` the only entry point.** The plugin loader ignores it whenever `skills/` exists, and never exposes a bare `/<plugin>` (S1g and the fixtures, both versions). Evals via `--plugin-dir` therefore can't reach it, and probably neither can marketplace installs (UNTESTED).
   - **Two layouts work.** Either put the orchestrator in `skills/<entry>/SKILL.md`, or ship the root SKILL.md with no `skills/` directory, where it registers as `<plugin>:<name>`. Either way, the spec's "one copy serves both channels" needs this change.
   - **The skills-dir channel stays plan A for now.** Whether it loads agents and hooks at user scope is UNTESTED. Re-test before P5 in an interactive session (user scope, or a trusted scratch project), and keep the local-directory marketplace as the fallback.
   - **Don't trigger risk 1's fallback on S1.** Its missing marker came from the trust gate, not a format failure.
2. **Trust.** A project skills-dir plugin loads only after someone accepts the workspace trust dialog interactively; `-p` never loads it (both versions).
   - The README should say: open the folder in Claude Code, accept trust, then run `/reload-plugins`.
   - CI and evals should use `--plugin-dir`.
3. **Hook form.** Use exec form: `"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/x.mjs"]`. Confirmed: no shell in the chain, the placeholder expands, and the env var is set.
   - Hooks fail open when the interpreter is missing, so the `permissions.deny` backstop stays mandatory.
   - The doctor should check that `node` is on PATH.
4. **PowerShell matcher.** `Bash|PowerShell` matches the PowerShell tool. On 2.1.228 that tool exists in `-p` with no env var set, and hook input carries `tool_name: "PowerShell"` and `tool_input.command`. Every v2 guard should list `PowerShell`; the spec's side finding about Chiron's matcher holds.
5. **Prompt hooks.** A `type: prompt` Stop hook works inside a plugin's `hooks.json`: it forced a revision, with `num_turns` 2.
   - Budget one extra turn per block.
   - Users see "Stop hook error occurred" on every block, so word the reason for them.
6. **Eval availability.** `claude plugin eval` exists on 2.1.228 but is gated ("currently in early access").
   - On 2.1.292 it works against a path.
   - Non-interactive runs need `--trust-plugin`, and `--no-publish` keeps the report off claude.ai.
   - P6 and the Done-means gates therefore require 2.1.292 or later.
   - `name@skills-dir` targets are UNTESTED.
7. **Sandbox recipe** for spikes, evals and the gauntlet: `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` + `--setting-sources project` + `--plugin-dir <dir>` + `--no-session-persistence` + `--model <full id>`.
   - Expect claude.ai connectors to load anyway.
   - Not usable: `--safe-mode` (drops plugin skills and agents), `--bare` (API key only), a scratch `CLAUDE_CONFIG_DIR` (no auth).
8. **Cost measurement.** `claude --plugin-dir <dir> plugin details <name>` gives the always-on cost of an uninstalled harness on 2.1.228, so `doctor` and P3 can use it. The catalog cache covers 204 official plugins, but its figures date from 2026-05-29 and use older models.
9. **Version gating.** Don't gate on `claude --version` alone: here it reports 2.1.228 while VS Code sessions run 2.1.292.
   - Preflight should report both versions: the PATH CLI and the VS Code extension folder.
   - Gate on the version the user will actually run. The `-p` init event carries `claude_code_version`.
10. **Model pinning.** Use full model IDs in every scripted run. `sonnet` and `opus` resolve to 5, not 5.5, on 2.1.228; `haiku` resolves to 4.5 on both versions.
11. **diagram-design.**
    - `py -3 -I` works for gate 3.
    - Pre-answer the style gate with the `profile: default` marker. It creates `~/.diagram-design/profiles/default.md` once; record that in the manifest so reset can remove it.
    - Dark mode is the page's job.
    - self_check and `check-page`'s no-`<script>` rule agree.
12. **Catalog.** The on-disk sources are 4 cloned marketplaces, 1 directory marketplace and the official catalog cache (204 entries). The official marketplace isn't added here, and `tags` is near-empty, so search `category` + `description`.
